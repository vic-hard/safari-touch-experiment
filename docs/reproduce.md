# Как воспроизвести прогон

Два способа: **проверить наши числа** по выгруженным данным (5 минут, телефон не нужен) и
**повторить съёмку** на своём устройстве (около часа с телефоном в руках). Результаты —
`docs/findings.md`, постановка и критерии — `PLAN.md`.

## Что нужно

| | |
|---|---|
| Python | 3.8 или новее, **только стандартная библиотека** — ни pip, ни виртуального окружения не требуется |
| Node | не нужен вовсе; страницы — ванильный JS без сборки |
| Телефон | для проверки чисел не нужен; для съёмки — iPhone с Safari (у нас iPhone 15, iOS 18.7.5) |
| Туннель | для съёмки: `cloudflared` (`winget install --id Cloudflare.cloudflared`) или любой другой, дающий https |

Проверка, что Python видит проект:

```powershell
python analysis/analyze_clock.py --help
```

## Способ 1. Проверить наши числа

Данные лежат в `data/`, семь файлов, 1.9 МБ. Целостность — `data/manifest.txt`, там sha256 по
каждому файлу:

```powershell
python -c "import hashlib,io;print(hashlib.sha256(io.open('data/20260916-130307-probe-p1-s1-both.json','rb').read()).hexdigest())"
```

Дальше три команды закрывают все десять критериев.

### A2, A3 — часы и метка события

```powershell
python analysis/analyze_clock.py data/20260916-130307-probe-p1-s1-both.json
```

Ожидается: гранулярность `performance.now()` = 1 мс, период кадра 17.000 мс, задержка входа в
обработчик `nowMs − timeStamp` = 18.8 ± 5.0 мс.

### A4–A8 — тайминг

```powershell
python analysis/analyze_timing.py data/20260916-130307-probe-p1-s1-both.json
python analysis/analyze_timing.py data/20260916-131407-collect-p1-s1-both.json
```

Первая команда даёт A4: по шкале `timeStamp` контроль метода проходит — `pointermove` даёт
полосу (R=0.683), `pointerdown` равномерен (R=0.108, p=0.79). Вторая даёт A5, A6 и A8: 60 DOWN
и 60 UP без потерь, СКО попадания по метроному 33.7 мс при вкладе кадра 4.91 мс.

Отсечку врабатывания для A8 можно менять — таблица чувствительности печатается всегда:

```powershell
python analysis/analyze_timing.py data/20260916-131407-collect-p1-s1-both.json --warmup 15
```

Вместе с A4 печатается контроль, не зависящий от журнала кадров: сетка ввода берётся из
интервалов между `move` внутри самого контакта. Он нужен там, где частота обновления экрана
плавает: на одном из Android-телефонов панель на время касания уходит на 120 Гц, интервалы между
кадрами рядом с тапом вдвое короче, и штатное смещение от границы кадра даёт «полосу»
механически.

Контроль задаёт два вопроса по порядку. Первый — **есть ли вообще жёсткая сетка**: если
интервалы между `move` внутри контакта гуляют, квантоваться DOWN не по чему, и второй вопрос не
ставится. Так на обоих iPhone (разброс интервалов ×2…×4) и на одном из двух Android-телефонов.
Второй — лежит ли DOWN на сетке, если она есть: у `ysa` шаг 8.30 мс с разбросом 2%, и фаза DOWN
на нём даёт полосу (R=0.95…0.99).

Без первого вопроса второй врёт: на неровном каденсе остаток от деления на «период» — это шум,
который на полусотне контактов случайно собирается в полосу.

A4 воспроизводится независимо на площадных сериях (в серии по метроному `move`-событий почти
нет, и скрипт там честно отказывается делать вывод):

```powershell
python analysis/analyze_timing.py data/20260916-132000-collect-p1-s1-both.json
python analysis/analyze_timing.py data/20260916-132255-collect-p1-s2-both.json
python analysis/analyze_timing.py data/20260916-132552-collect-p1-s3-both.json
```

### A1, A10 — площадь

```powershell
python analysis/analyze_area.py data/20260916-132000-collect-p1-s1-both.json data/20260916-132255-collect-p1-s2-both.json data/20260916-132552-collect-p1-s3-both.json --holdout data/20260916-132552-collect-p1-s3-both.json
```

Ожидается: ступени `radiusX` кратны 12.077; диагностика динамики покажет, что у Touch значение
внутри контакта не меняется ни разу, а у Pointer меняется в 64 контактах из 117; A10 считается
по обоим потокам и на отложенной серии даёт 30/30 мягких при 14/30 отсеянных резких по Touch и
25/30 по Pointer.

Ключ `--source touch|pointer` считает только один поток; по умолчанию печатаются оба, потому
что они несут разную информацию.

Последний позиционный файл и так считается отложенным, `--holdout` указан явно для
однозначности. Полезные ключи: `--csv out/area.csv` — выгрузка признаков по контактам,
`--source touch|pointer` — по какому потоку считать, `--include-partial` — не исключать
прерванные серии (по умолчанию исключаются).

### Разделимость градаций у нового участника

Первое, что считается по сериям нового человека, — есть ли в канале что разделять. Порог здесь
не при чём: он и на неразделимых данных выглядит нормально.

```powershell
python analysis/analyze_features.py data/20260921-161053-collect-user6-s1-both.json data/20260921-161302-collect-user6-s1-both.json --thresholds "area50=1e12,shift50=1e12"
```

Ожидается раздел «разделимость градаций в канале»: AUC площади 0.47 при p = 0.428, AUC
микросдвига 0.52 при p = 0.231, предупреждение, что ни один признак фильтра градации не
различает, и отдельной строкой AUC длительности 0.02 при p = 0.001 — то есть градации участник
различал, но не тем, что видит фильтр. Для сравнения, те же строки на сериях `victor`
(`20260919-153218` и `20260919-153345`) дают 0.93 и 0.88 при p = 0.001. Правило чтения —
`docs/protocol.md`, раздел «Проверка разделимости».

### Проба канала ускорения

Отдельный скрипт, в общий анализ не встроен: пока не известно, отвечает ли канал, признаку
нечего делать в правиле фильтра.

```powershell
python analysis/analyze_motion.py data/<серия в руке>.json data/<серия на столе>.json
```

Разделы M1–M5: канал (разрешение и частота), шкала меток, покрытие окна 50 мс отсчётами, хват
по фоновому шуму, и `accel50` с AUC по градациям. Решающее правило — в `docs/protocol.md`,
раздел «Проба канала ускорения»; скрипт печатает вывод по нему сам и не даёт подвинуть границы
задним числом.

## Способ 2. Повторить съёмку

### Ш1. Поднять стенд

```powershell
python server/server.py
cloudflared tunnel --url http://localhost:8000
```

Открыть на телефоне https-адрес из вывода `cloudflared`. **Только https через туннель**: по
LAN-адресу входящие соединения к дев-серверу блокирует брандмауэр Windows, а часть браузерных
API без https недоступна.

Проверка, что сервер жив: `http://localhost:8000/health` отвечает `{"ok": true}`.

Пока туннель работает, стенд доступен всему интернету, а аутентификации у сервера нет:
поднимать на время съёмки и гасить сразу после. Подробности — раздел «Безопасность» в
[README](../README.md).

### Ш2. Подготовить телефон

- Открыть ссылку **именно в Safari**. Встроенный браузер мессенджера не годится: это другой
  процесс с другими ограничениями. Страница это проверяет сама — если сверху красная плашка и
  кнопка «Старт» подписана «нужен Safari», надо нажать «Поделиться» → «Открыть в Safari».
- Настройки → Экран и яркость → Автоблокировка: **Никогда**. Если экран погаснет, кадры
  встанут и привязка событий к кадрам (A4) потеряет смысл.
- Переключатель «Бесшумно» **выключить** — для серии по метроному нужен звук из динамика.
  Беспроводные наушники не использовать: они добавят собственную задержку.
- Заряд выше 50%, режим энергосбережения выключен: он срезает частоту обновления.
- На главной странице заполнить метаданные: участник, номер серии, заряд, режим
  энергосбережения, заметки. Они запоминаются и подставляются во все режимы.

### Ш3. Снять серии

Во время каждой серии не уводить Safari в фон и не открывать Пункт управления: в логе внизу
страницы появится «кадры не идут», и серию придётся переснять. На последнем тапе страница
просит отпустить палец — отпустить и только потом жать «Выгрузить».

| # | режим | протокол | номер серии | зачем |
|---|---|---|---|---|
| 1 | Э1 «пробник каналов» | 20 тапов: 10 мягких, 10 резких | 1 | A1, A2, A3, A4 |
| 2 | Э3 → «тайминг: 60 тапов по метроному» | 60 тапов в щелчок | 1 | A5, A6, A8 |
| 3 | Э3 → «площадь: 60 тапов» | 30 мягких + 30 резких | **1** | A10, обучающая |
| 4 | Э3 → «площадь: 60 тапов» | то же | **2** | A10, обучающая |
| 5 | Э3 → «площадь: 60 тапов» | то же | **3** | A10, отложенная |
| 6 | Э3 → «контроль: только Touch» | 20 тапов | 4 | A7 |
| 7 | Э3 → «контроль: только Pointer» | 20 тапов | 5 | A7 |

**Номер серии перед каждой площадной обязательно менять.** По нему страница переключает
порядок блоков: в чётных сериях она начинает с резких. Если номер не менять, все три серии
пойдут в одном порядке, и эффект градации будет не отличить от эффекта «первые десять тапов
всегда мягче».

Градации: **мягко** — подушечкой пальца, без нажима; **резко** — кончиком, коротко и жёстко.
Две градации, не четыре: четыре ступени надёжно не разделяются ничем (SF §3.3).

После каждой серии — «Выгрузить». В логе должно появиться две строки: сначала
`[ok] POST: ...` (файл лёг в `data/` на ноутбуке), затем `[ok] файл: ...` (копия в Files app).
Если POST не прошёл, серия всё равно сохранена файлом — её надо перенести в `data/` руками.

Прерванную серию (дрогнул палец, сбился) выгружать не нужно: у неё недобран последний блок
градаций. Если она всё же попала в `data/`, скрипт анализа исключит её сам и скажет об этом.

### Ш4. Посчитать

Те же команды, что в способе 1, но по своим файлам. Имена файлов сервер формирует из
метаданных: `<дата>-<время>-<страница>-<участник>-s<серия>-<режим>.json`.

## Что должно совпасть, а что нет

**Совпасть обязано** — иначе что-то не так с прогоном:

- контроль метода в A4: `move` даёт полосу, `down` по шкале `timeStamp` — нет (на WebKit;
  в Chrome на Android штатный контроль не проходит, и вывод делается по контролю на сетке
  `move`);
- `timeStamp` у `pointerdown` и `touchstart` совпадает с точностью до тика часов (1 мс);
- `pointerdown` приходит раньше `touchstart`;
- потери контактов близки к нулю;
- мягкие тапы не дотягивают до верхних ступеней радиуса.

**Совпасть не обязано** — зависит от устройства и человека:

- сами ступени радиуса (у другой модели iPhone шаг может быть другим);
- СКО попадания по метроному: это в основном разброс конкретного человека;
- доля отсеянных резких в A10: зависит от того, насколько отчётливо человек бьёт «резко»;
- постоянные смещения — задержка вывода звука, средняя задержка доставки.

## Грабли, на которые мы наступили

Перечислены, чтобы не тратить на них время повторно. Все, кроме первой, уже исправлены в коде.

1. **Ссылка, открытая во встроенном браузере мессенджера.** Съёмка идёт, выгрузка не проходит,
   и это вообще не Safari. Теперь страница определяет среду и блокирует старт.
2. **Однопоточный сервер.** `HTTPServer` обслуживает одно соединение за раз, туннель держит
   соединения открытыми, и выгрузка встаёт в очередь до таймаута — на телефоне это выглядит
   как `POST не прошёл: Load failed`. Сервер переведён на `ThreadingHTTPServer`.
3. **Порядок выгрузки.** Скачивание файла, запущенное до `fetch`, обрывает незавершённые
   запросы страницы в iOS Safari. Теперь сначала POST, потом файл.
4. **Кадры останавливаются в фоне.** Если страница уходит из фокуса, `requestAnimationFrame`
   встаёт, и A4 теряет смысл молча. Добавлен сторож кадров: предупреждение в лог, счётчик
   простоев в метаданные, отказ считать A4 в анализе.
5. **Врабатывание в серии по метроному.** Первые тапы человек ловит долю, и их включение в
   расчёт завышает СКО втрое. Отсечка зафиксирована заранее, её влияние печатается всегда.

## Отладка без Web Inspector

Web Inspector требует macOS. Вместо него — лог прямо на странице (`web/js/log.js`, туда же
перехватываются исключения) и POST сырых данных на ноутбук. Сырые поля события и есть
результат эксперимента: смотреть их надо в JSON, а не в консоли.

## Чего делать нельзя

- **Синтетический ввод.** Симулятор iOS и скриптовые тапы невалидны и для площади, и для
  тайминга (PLAN §8) — по той же причине, по которой в TouchLab запрещён `adb shell input`.
  В `data/` синтетика не кладётся.
- **Менять ориентацию, яркость или режим энергосбережения посреди серии.**
- **Делать выводы по одной серии.** Отложенная серия обязательна: в этом самом прогоне порог,
  дававший 28/30 внутри обучающей серии, на отложенной дал 14/30.
