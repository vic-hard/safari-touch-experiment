# Safari Touch Experiment — план выполнения

Проверка на iPhone 15 / Safari двух независимых вопросов заказчика. Эталон для сравнения — нативный Android-сбор проекта TouchLab, решение по мягкости зафиксировано в `TouchLab/docs/softness-filter.md` (далее — SF с номером раздела).

Дата составления: 14.09.2026. Устройство: iPhone 15 (не Pro). Разработка: Windows + VS Code.

## 1. Два вопроса, и они независимы

**В1 — площадь.** Отдаёт ли Safari геометрию контактного пятна (`radiusX`/`radiusY`) и
различает ли она мягкие и резкие тапы так же, как `size` на Android (SF §4: 60/60 мягких пропущено, 27/30 очень резких отсеяно).

**В2 — тайминг DOWN.** Каковы фактические timestamp и распределение интервалов
`pointerdown`/`pointerup`. Утверждение «все touch-события приходят строго по кадрам 60 Гц»
не проверено: WebKit действительно склеивает move-события с кадрами, но у
`touchstart`/`pointerdown` отдельная обработка. Для ритм-игры значим момент DOWN, а не вся траектория пальца, поэтому редкие промежуточные отсчёты площади не обязательно портят ритмический тайминг.

**Порядок работ от этого меняется.** В2 не зависит от исхода В1: даже если геометрия
мертва, вопрос о ритме остаётся осмысленным и отвечаемым. Поэтому пробник по площади (Э1)
гейтит только площадную половину, а тайминговый стенд (Э2) строится в любом случае.

**Канал силы нажатия закрыт заранее.** 3D Touch убран начиная с iPhone 11, на iPhone 15 его
нет: `Touch.force` = 0, `touchforcechange` не сработает. Проверять нечего, мерить можно
только геометрию пятна и время — ровно та же ситуация, что с мёртвым `pressure` на
SM-A525F (SF §2).

## 2. Что измеримо со страницы, а что нет

Это главный раздел плана: половина ожиданий от такого эксперимента обычно нереализуема, и
лучше знать об этом до, а не после.

### Измеримо изнутри страницы

| величина | как |
|---|---|
| гранулярность часов | busy-loop по `performance.now()`, сбор различных значений |
| несёт ли `timeStamp` собственную информацию | разница `event.timeStamp` и `performance.now()` на входе в обработчик |
| квантование `timeStamp` | распределение дробной части и распределение разностей |
| привязка DOWN к кадру | смещение события от предыдущей границы кадра, гистограмма |
| интервал DOWN→UP | разность меток пары, распределение и квантование |
| потери контактов | счётчики `pointerdown` без пары, `pointercancel` |
| расхождение Touch и Pointer | оба потока на одном элементе, сравнение меток и полей |
| разброс попадания по метроному | отклонение DOWN от запланированной доли, СКО |
| геометрия пятна | `radiusX`/`radiusY`/`rotationAngle`, `width`/`height`/`pressure` |
| склейка | наличие и длина `getCoalescedEvents()`/`getPredictedEvents()` |

### Не измеримо изнутри страницы

**Абсолютная задержка «палец коснулся стекла → сработал обработчик».** Внутри страницы нет
эталона момента физического касания; любая метка времени события уже принадлежит той
системе, задержку которой мы хотим измерить. Нужна внешняя инструментовка — см. Э6,
отдельный необязательный этап.

**Разделение человеческого и системного джиттера по одной серии.** Разброс попадания по
метроному — это свёртка разброса человека и разброса системы. Решению это не мешает:
критерий A8 сформулирован как сравнение с величиной квантования, а не с нулём.

## 3. Критерии приёмки

Нумерация в стиле TouchLab: критерий → чем подтверждён. Заполняется в `docs/findings.md` по
факту прогона.

| # | критерий |
|---|---|
| A1 | Известно, меняются ли `radiusX`/`radiusY` от характера тапа или являются константой |
| A2 | Известна фактическая гранулярность `performance.now()` на устройстве |
| A3 | Известно, отличается ли `event.timeStamp` от `performance.now()` в обработчике, то есть несёт ли метка события собственную информацию |
| A4 | Известно распределение смещения `pointerdown` от границы кадра, то есть квантуется ли DOWN по кадрам |
| A5 | Известно распределение интервала `pointerdown`→`pointerup` и его квантование |
| A6 | Известна доля потерянных и отменённых (`pointercancel`) контактов за серию |
| A7 | Известно расхождение потоков Touch Events и Pointer Events по меткам времени и по набору полей |
| A8 | Известно СКО попадания по метроному и его отношение к величине квантования кадра |
| A9 | Все выводы получены скриптом по выгруженным данным, а не наблюдением на экране |
| A10 | Для площади: результат выражен в той же мере, что SF §4 — доля пропущенных мягких и отсеянных резких на отложенной серии |

| этап | содержание | оценка |

| Э0 | стенд: сервер, туннель, выгрузка, лог на странице | 1–1.5 ч |

Итого без Э6: **10–14 часов**. Оценка заказчика в 3–6 часов покрывает примерно Э1 плюс
часть Э2 — то есть код страницы, но не стенд, не съёмку и не анализ. Ответ на вопрос даёт
именно анализ.

## 6. Стенд (Э0)

**Доставка страницы.** `cloudflared tunnel --url http://localhost:8000` — быстрый туннель,
один exe, регистрация не нужна, отдаёт https-адрес. HTTPS берём сразу, даже если
акселерометр не понадобится: он снимает целый класс вопросов «почему тут не работает», а
для `DeviceMotion` он обязателен. Запасной вариант на время съёмки — GitHub Pages.

**Отладка.** Web Inspector требует macOS, его не будет. Вместо него лог прямо на странице
(`js/log.js`) плюс POST сырых данных на ноутбук. Это не обходной путь, а штатный: сырые поля
события и есть результат эксперимента, смотреть их надо в файле, а не в консоли.

**Выгрузка — два пути одновременно.** Основной: POST на свой же сервер через тот же туннель
(один origin, никакого mixed content, JSON падает в `data/`). Страховка: скачивание файлом в
Files app на случай обрыва сети посреди серии. Терять снятую серию из-за Wi-Fi нельзя —
повторить её в тех же условиях невозможно.

**Мелочь, которая съедает вечер:** брандмауэр Windows блокирует входящие соединения к
дев-серверу из локальной сети. При работе через туннель это не всплывает, при работе по
LAN-адресу — всплывает обязательно.

## 7. Методика измерений

### 7.1 Калибровка часов (A2, A3) — делается первой

Прежде чем что-то утверждать о квантовании событий, надо знать квантование самих часов. Это
прямой аналог `quantization`-члена в `ClockSyncCapture` из TouchLab: если часы тикают раз в
миллисекунду, ни одна метка события не может быть точнее миллисекунды, и любой вывод о
привязке к кадрам обязан это учитывать.

Порядок: цикл на ~200 мс, читаем `performance.now()`, собираем множество различных значений,
берём минимальную положительную разность. Ожидаемо около 1 мс (защита от Spectre), но это
надо получить, а не предположить. Тут же фиксируются `performance.timeOrigin`, `Date.now()`,
`navigator.userAgent`, `screen.*`, `devicePixelRatio`.

Отличить квантование часов (1 мс) от квантования по кадрам (16.7 мс) на гистограмме
несложно — величины расходятся в шестнадцать раз.

### 7.2 Привязка DOWN к кадру (A4) — центральное измерение

Постоянный цикл `requestAnimationFrame` пишет метку каждого кадра. В обработчике
`pointerdown` записываются `performance.now()`, метка последнего кадра и его номер. Признак —
смещение события от предыдущей границы кадра.

- Смещения сбиваются в узкую полосу → DOWN квантуется по кадрам.
- Смещения равномерны по интервалу кадра → DOWN приходит вне кадровой сетки, разрешение
  лучше кадра.

**Обязательный контроль метода:** то же смещение считается для `pointermove`. Move-события
заведомо склеены с кадрами, поэтому их смещения обязаны собраться в полосу. Если у move
полоса, а у down равномерно — метод работает и вывод состоятелен. Если полоса у обоих или ни
у одного — сначала чиним метод, потом делаем выводы.

### 7.3 Два потока рядом (A7)

`touchstart`/`touchend` и `pointerdown`/`pointerup` вешаются на один элемент и пишутся в один
журнал. Это ничего не стоит и вдвое увеличивает информацию: вполне возможно, что `touchstart`
несёт `radiusX`, а у `pointerdown` `width`/`height` равны единице.

Подводный камень: `preventDefault` и `touch-action` на одном потоке могут исказить другой.
Поэтому кроме совмещённой серии снимаются две контрольные — только Touch и только Pointer, по
20 тапов. Если метки в совмещённом режиме отличаются от одиночных, выводы строятся по
одиночным.

### 7.4 Метроном (A8) — то, ради чего всё затевалось

Щелчки планируются через Web Audio по `AudioContext.currentTime` — собственные часы звукового
движка, не зависящие от кадров. Метки долей переводятся в шкалу `performance.now()` через
`getOutputTimestamp()`; если он недоступен, через один замер соответствия в начале сессии, с
пометкой о худшей точности.

Меряется **СКО отклонения DOWN от доли, а не среднее**. Постоянная задержка вывода звука
(динамик, воздух, `baseLatency`) сдвигает среднее и не влияет на разброс, а для ритм-игры
значим именно разброс.

**Как читается результат.** Равномерное квантование по кадру даёт вклад в СКО
16.7/√12 ≈ 4.8 мс. Разброс человека, отбивающего ритм, обычно кратно больше. Поэтому критерий
A8 сформулирован не как «квантуется или нет», а как «виден ли вклад квантования на фоне
человеческого разброса». Если не виден — web годится для ритм-игры даже при кадровом
квантовании, и это ответ заказчику по существу.

### 7.5 Площадь (A1, A10)

Признак и методика берутся из SF без изменений, чтобы числа были сопоставимы:

- признак — максимум площади за контакт (SF §5: максимум, а не первый отсчёт, потому что
  фильтр живёт на краю распределения);
- обучение на двух сериях, проверка на третьей отложенной (SF §2);
- порог — максимум признака по мягким тапам обучающих серий;
- результат выражается как «сколько мягких прошло / сколько резких отсеяно» (SF §4).

Абсолютные пороги с Android несопоставимы — другой сенсор, другие единицы. И не нужны: по
SF §6 порог и так калибруется под игрока.

**Две градации, не четыре.** SF §3.3: четыре ступени не разделяются надёжно ничем, потолок в
разметке, а не в признаках; четыре градации были нужны для имитации игровой сессии, а не как
выход системы. Здесь задача — фильтр, поэтому мягко/резко.

## 8. Протокол съёмки (Э4)

Окончательно заполняется после Э1, каркас такой:

**Тайминговые серии.** 3 серии по 60 тапов по метроному (100 BPM, доля 600 мс) плюс 40
свободных тапов на распределение длительности контакта. Серии в разное время суток, как в
пилоте TouchLab.

**Площадные серии** — только если Э1 дал живую геометрию. 3 серии по 60 тапов, 30 мягких и 30
резких, порядок градаций между сериями меняется.

**Фиксируется в метаданных каждой сессии:** участник, номер серии, время, режим
энергосбережения и уровень заряда (Low Power Mode срезает частоту), версия iOS, ориентация,
яркость. Без этого повторный прогон не сопоставить с первым.

**Синтетический ввод запрещён.** Симулятор iOS и любые скриптовые тапы невалидны для
измерения площади и тайминга по той же причине, по которой в TouchLab запрещён
`adb shell input`. Симулятор всё равно недоступен без Mac, так что потери нет.

## 9. Формат данных

Один JSON на сессию, версия формата в поле `format`, начинаем с `web-probe-0.1.0`.

```
{
  "format": "web-probe-0.1.0",
  "meta":   { участник, серия, режим, устройство, экран, время старта },
  "clock":  { гранулярность, timeOrigin, соответствие аудио-часам },
  "frames": [ метки кадров rAF ],
  "events": [ по событию: тип, timeStamp, now в обработчике, номер и метка
              последнего кадра, координаты, все поля обоих потоков ]
}
```

Недоступные значения пишутся явным `null`, а не опускаются и не заменяются умолчанием —
конвенция TouchLab (критерий 33). Константа в канале записывается как есть: это честная
запись, а не брак.

## 10. Риски

| риск | что делаем |
|---|---|
| `radiusX`/`radiusY` окажутся константой | Э1 отвечает за час; тогда остаются длительность и движение пальца, а по SF §3.4 они к фильтру не добавили ничего — площадная половина закрывается отрицательным результатом, и это нормальный результат |
| `force` = 0 | известно заранее, в план не заложено |
| Safari перехватывает жесты у краёв, pull-to-refresh, двойной тап | `touch-action: none`, пассивность слушателей выключена, зона тапа далеко от краёв и от полосы home indicator, отдельный счётчик `pointercancel` (A6) |
| Low Power Mode срезает частоту | фиксируется в метаданных, серии снимаются при заряде выше 50% |
| нет Web Inspector | лог на странице плюс POST сырых данных |
| один участник, одно устройство | то же ограничение, что SF §9; в отчёте указывается явно, на выводы о калибровке не претендуем |
| вывод по одной серии | отложенная серия обязательна: SF §3.1 — скорость роста площади дважды разделяла группы на всех данных и разваливалась на проверке |

## 11. Что в план не входит и почему

- **Chrome Android и pure web на обеих платформах.** По уточнению заказчика — только позже и
  только если решим идти в pure web. Сравнение идёт с уже имеющимися результатами нативного
  Android.
- **Акселерометр.** SF §7: выигрыш не соразмерен трудозатратам на MVP. Может вернуться, если
  Э1 даст отрицательный результат и геометрии не будет вовсе — тогда это единственный
  оставшийся физический канал.
- **Изменение схемы TouchLab.** Веб-эксперимент не трогает Android-сторону: SF §8.
- **Живая оценка мягкости во время касания.** Отдельная доработка, оценивается отдельно.
